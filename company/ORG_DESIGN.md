# Kaz Company 組織設計書（v0.1 草案）

Claude Code を「一つの会社」として運営するための組織設計。社長 = Kaz。

---

## 0. 前提：Claude Code の仕組みとの対応づけ

組織図をそのまま Claude Code に載せると、技術的な制約に当たる。

| 会社の概念 | Claude Code での実体 | 備考 |
|---|---|---|
| 社長 | Kaz（人間） | 決裁・承認・外部送信の最終判断 |
| 副社長 | 各セッションのメイン Claude ＋ 全社 `CLAUDE.md`（社是・ルーティング規則） | 「誰に振るか」を判断する窓口 |
| 部署（プロジェクト） | 部署ごとの作業場所（リポジトリ or ディレクトリ）＋ 部署 `CLAUDE.md` | 部署長はここに書く「部の方針」 |
| 社員（役割） | サブエージェント（`.claude/agents/*.md`）とスキル（`.claude/skills/`） | 役割ごとに1ファイル |
| 社内記憶・議事録 | Notion（DB）または Git リポジトリ | クラウドセッションは使い捨てなので、残すものは外に置く |
| 決裁箱 | Notion「決裁待ち」DB | 副社長が積み、社長が処理 |

**重要な制約：サブエージェントは、さらにサブエージェントを呼べない（入れ子は1段まで）。**
そのため「副社長 → 部長 → 社員」の3階層を、エージェント同士の呼び出しでは組めない。実際には次のように平らに組む。

- **部長** = 部署ごとの `CLAUDE.md` とスキル（＝その部の進め方を決めた手順書）
- **副社長** = その手順書に沿って社員（サブエージェント）を並列に動かし、結果をまとめる
- 部署をまたぐ大きな案件だけ Workflow（多エージェント編成）や別セッションを使う

## 1. 組織図

```
社長（Kaz）
 └─ 副社長（Chief of Staff）＝ 総合窓口・秘書室
     ├─ 秘書室（副社長直轄）……メール・予定・朝の報告・決裁箱
     ├─ 臨床支援部 ……………………日常臨床の相談
     ├─ 治験事務局 ……………………CLIVO試験ほか
     ├─ 研究企画部 ……………………研究提案（テロメライシン等）＋壁打ち
     ├─ 語学研修部 ……………………英語学習（IELTS Speaking 6.5）
     ├─ 生活相談部 ……………………日常生活・健康
     ├─ 財務部 …………………………副業・資産・税
     ├─ 広報部（新設提案）……………Instagram論文発信・学会スライド
     └─ 共通サービス（全部署から呼べる）
         ├─ 文献調査センター（PubMed）
         ├─ 品質保証室（事実確認・引用確認）
         └─ 文書制作室（スライド/Word/Excel/文章の人間らしさ）
```

## 2. 部署と役割

### 2-1. 副社長（Chief of Staff）
- **職務**：依頼の受付と部署への振り分け、部署間の連携、決裁待ちの管理、全社の記録。
- **権限ルール**
  - メール送信・予定の確定・外部への公開は**必ず社長の承認後**（下書きまでは自由）
  - 迷ったら聞く。ただし聞く前に、選択肢と推奨案を用意する
- **秘書室（直轄）**
  | 役割 | 仕事 | 使う道具 |
  |---|---|---|
  | メール係 | 受信の仕分け（要返信／要決裁／参考）、返信の下書き | Gmail |
  | 予定係 | 予定登録、日程調整案、締切リマインド | Google Calendar |
  | 朝の報告係 | 当日の予定・未返信・締切・決裁待ちを毎朝まとめる | `morning` スキル、定期実行 |
  | 記録係 | 決定事項・議事録・各部の進捗を Notion に残す | Notion |

### 2-2. 臨床支援部（日常臨床の相談）
| 役割 | 仕事 |
|---|---|
| 部長 | 相談の整理（何が問われているか／緊急度）、回答の取りまとめ |
| エビデンス調査員 | PubMed・ガイドラインの確認。MeSH で検索式を立て、件数で妥当性を確かめてから検索 |
| 薬剤チェック係 | 用量・相互作用・腎機能や肝機能による調整・禁忌 |
| セーフティ係 | 見逃してはいけない疾患、AI の回答の限界の明示 |
| **CQ ハンター** | 相談の中から「答えが無い／割れている」疑問を拾い、**研究企画部の CQ バックログに登録**する |

> CQ ハンターを臨床支援部に置き、研究企画部とつなぐのがこの組織の要。日々の臨床相談がそのまま研究テーマの種になる。

### 2-3. 治験事務局（CLIVO 試験など）
| 役割 | 仕事 |
|---|---|
| 事務局長 | 試験ごとの進捗と課題の一覧、優先順位づけ |
| 文書管理係 | プロトコル・手順書・版管理、改訂差分の要約 |
| 登録・進捗係 | 施設ごとの登録状況、目標との差、督促文の下書き |
| 安全性・逸脱係 | 重篤な有害事象や逸脱の報告期限・様式の確認 |
| 規制・倫理係 | 臨床研究法／GCP、倫理審査委員会への提出物チェックリスト |
| 会議係 | 会議の議題・資料・議事録、宿題の追跡 |
| 問い合わせ対応係 | 施設からの質問への回答案（FAQ として蓄積） |

> **守秘ルール**：被験者の個人情報や、依頼者の機密資料の原本はクラウドに置かない。仮名化したもの、または公開情報だけを扱う。

### 2-4. 研究企画部（研究提案＋壁打ち）
「研究提案」と「試験提案の壁打ち」は同じ部署にまとめ、**進め方の違い（モード）**として扱う。

| 役割 | 仕事 |
|---|---|
| 部長（PI 補佐） | 研究の問いを PICO/PECO に落とし込み、提案書の骨格を作る |
| 調査部 | 先行研究、進行中の試験（ClinicalTrials.gov / jRCT）、空白領域の洗い出し |
| **批判的レビュアー（上司役／査読者役）** | 新規性・実現可能性・倫理・バイアスを容赦なく突く。**結論を渡さず資料だけを渡し**、独立した文脈で読ませる |
| 生物統計担当 | 主要評価項目、サンプルサイズ、解析計画、中間解析、多重性 |
| 規制・倫理担当 | 臨床研究法の適用の有無、先進医療、同意・利益相反 |
| 資金獲得担当 | AMED・科研費・企業との共同研究の公募要件との突き合わせ |
| 執筆担当 | 研究計画書・抄録・申請書のたたき台 |

**壁打ちモード**：社長の案に対して、レビュアーと統計担当が質問を返す形式で進める（答えを先に出さない）。
**CQ バックログ**：臨床支援部から上がってきた疑問を Notion の DB で管理する（重要度・実現性・状態）。

### 2-5. 語学研修部（英語）
| 役割 | 仕事 |
|---|---|
| 日記コーチ | 日本語の日記を英訳し、文法を解説（`diary-english-coach`） |
| スピーキング相手 | IELTS Part 1〜3 の模擬面接と採点 |
| 医学英語校閲係 | 論文・抄録・メールの英文校閲（他部署からも呼べる） |
| 進捗係 | 弱点（時制・冠詞など）を記録し、出題に反映 |

### 2-6. 生活相談部
| 役割 | 仕事 |
|---|---|
| 生活アドバイザー | 家事・買い物・旅行・手続きの相談 |
| 健康管理係 | 運動・睡眠・食事（社長自身の健康） |

### 2-7. 財務部（副業・お金）
| 役割 | 仕事 |
|---|---|
| 家計・資産係 | 収支の見える化、資産配分の考え方 |
| 副業企画係 | 発信（Instagram 等）・講演・執筆の収益化、勤務先の副業規程の確認 |
| 税務係 | 確定申告（雑所得・事業所得）、経費の整理 |
| リスク監査係 | 投資話・節税スキームの懐疑的チェック |

> 個別の投資判断と税務の最終判断は専門家に確認する、という前提を部の規則に書いておく。

### 2-8. 広報部（新設提案）
すでに `kaz-instagram-paper` と `academic-slide-design` スキルがあるため、独立した部署にする価値がある。
| 役割 | 仕事 |
|---|---|
| ネタ探し係 | 面白い論文の発掘（研究企画部の調査結果も流用） |
| デザイン係 | Canva カルーセル、学会スライド |
| 編集係 | 文章の人間らしさ（`humanize`）、誤りの確認 |

### 2-9. 共通サービス
| 部署 | 仕事 | 主なスキル・ツール |
|---|---|---|
| 文献調査センター | MeSH 検索式→件数確認→検索→抄録取得、引用の書式統一（第一著者・雑誌・年＋リンク） | PubMed MCP、`pubmed-systematic-review`、`deep-research` |
| 品質保証室 | 出力の事実確認。特に**引用の実在確認（PMID と照合）**、数値の転記ミス | — |
| 文書制作室 | スライド・Word・Excel・PDF | `pptx` `docx` `xlsx` `pdf` `academic-slide-design` |

## 3. 運営ルール（全社 `CLAUDE.md` に入れる候補）

1. **承認の線引き**：外部送信・削除・予定の確定・お金が動くことは、社長の承認を必須とする。
2. **独立したレビュー**：批判役には結論を渡さない。資料だけを渡して読ませる。
3. **出典ルール**：医学的な主張には PubMed の出典を付ける。品質保証室が PMID を照合する。
4. **守秘ルール**：患者・被験者の識別情報は入力しない。治験資料は仮名化して扱う。
5. **記録ルール**：決定事項は Notion の「決定ログ」に一行で残す（日付・部署・決定・理由）。
6. **小さく始める**：まずは副社長＋3部署で回し、困りごとが出てから役割を増やす。

## 4. 導入ロードマップ

| 段階 | 内容 |
|---|---|
| 第1期 | 全社用の専用リポジトリ（例 `kaz-company-hq`）を作る。全社 `CLAUDE.md` と副社長のルーティング規則を置く。Notion に「決裁待ち」「決定ログ」「CQ バックログ」の3 DB を作る |
| 第2期 | 研究企画部（調査部・批判的レビュアー・統計担当）と臨床支援部（CQ ハンター）をサブエージェント化する |
| 第3期 | 秘書室の朝の報告を定期実行にする。治験事務局は試験ごとにチェックリストのスキルを作る |
| 第4期 | `find-skills` で既製スキルを探し（＝採用）、足りない部分は `skill-creator` で自作する（＝社内育成） |

## 5. 導入予定スキルの評価

| スキル | 役割 | 評価・注意 |
|---|---|---|
| **find-skills**（vercel-labs） | 人事部（外部採用）：skills.sh から既製スキルを検索・導入する | 便利。ただし第三者のスキルはプロンプトやスクリプトそのものなので、**導入前に中身を確認する**（悪意ある手順の混入対策） |
| **superpowers**（obra） | 業務手順の型（ブレインストーミング、計画書作成、サブエージェント駆動、検証） | 中心はソフトウェア開発向け（テスト駆動開発など）。研究企画の壁打ちには `brainstorming` と `writing-plans` が流用できる。一方で、既存の Codex 委譲ルールと手順が重なる場面があるため、優先順位を `CLAUDE.md` に明記する |
